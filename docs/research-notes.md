
## Research Notes

### Spotify OAuth

Which flow should SoundPrint use?
- It should use Authorization Code Flow with the PKCE extension.

Why this flow?
- The app has a frontend and I do not want to expose any client secrets.
- PKCE adds a code verifier and code challenge so the app can prove that the same client that started the login flow is the one exchanging the authorization code for an access token.

What happens in the flow?
1. The app generates a random `code_verifier`.
2. The app hashes the `code_verifier` to create a `code_challenge`.
3. The app redirects the user to Spotify's `/authorize` endpoint with the Client ID, redirect URI, requested scopes, `code_challenge`, and `code_challenge_method`.
4. Spotify asks the user to log in and approve the requested permissions.
5. Spotify redirects the user back to the `redirect_uri` with an authorization code.
6. The app exchanges the authorization code for an access token by sending a POST request to `/api/token` with the `code_verifier`.
7. The app uses the access token to make Spotify Web API calls.

Important terms:
- Client ID: A unique, public string generated by the Spotify Developer Dashboard that acts as your application's "username" for OAuth 2.0 authentication.
- Redirect URI: The specific web or application address that Spotify uses to return users to your application after they authorize or deny access to their Spotify accounts.
- Authorization code: A short-lived, temporary string issued by Spotify's OAuth 2.0 server after a user logs into their Spotify account and consents to your app's requested permissions.
- Access token: A string that contains the credentials and permissions that can be used to access a given resource.
- Refresh token: A secure credential that allows your app to request a new access token from Spotify without requiring the user to log in and reauthorize your application.
- Scopes: Permission tags that define exactly what user data your application wants to access.
- PKCE: An OAuth 2.0 security extension to let public client apps request user data without exposing a Client Secret.

To authorize:
- I need to create an app in the Spotify Developer Dashboard.
- The app gives me a Client ID.
- With PKCE, I should not expose a Client Secret in frontend code.


### Spotify Data Available

### Get User's Top Items

- Requires the authorization scope `user-top-read`.
- The request is handled through a GET request to `/me/top/{type}`.
- `type` is the entity to return: either `artists` or `tracks`.
- Other parameters include `time_range` for the time frame, `limit` for the maximum number of items to return, and `offset` for pagination.
- The response includes paging information such as `href`, `limit`, `next`, `offset`, `previous`, and `total`.
- The main useful field is `items`, which contains either `ArtistObject` or `TrackObject` data.
- For SoundPrint, this endpoint is useful because it can provide the user's strongest taste signals: their top artists and top tracks over different time ranges.

### Get Recently Played Tracks

- Requires the authorization scope `user-read-recently-played`.
- The request is handled through a GET request to `/me/player/recently-played`.
- Parameters include `limit` for the maximum number of items to return, `after` for returning items after a cursor position, and `before` for returning items before a cursor position.
- The response includes paging information such as `href`, `limit`, `next`, and `cursors`.
- The main useful field is `items`, which contains an array of `PlayHistoryObject`.
- Each `PlayHistoryObject` contains `track`, `played_at`, and `context`.
- For SoundPrint, this endpoint is useful because it can show the user's short-term listening behavior, including what they played recently and when they played it.

### Get Current User's Playlists

- Requires the authorization scope `playlist-read-private` if the app needs access to the user's private playlists.
- The request is handled through a GET request to `/me/playlists`.
- Parameters include `limit` for the maximum number of items to return and `offset` for the index of the first playlist to return.
- The response includes paging information such as `href`, `limit`, `next`, `offset`, `previous`, and `total`.
- The main useful field is `items`, which contains an array of `SimplifiedPlaylistObject`.
- Each `SimplifiedPlaylistObject` contains playlist metadata such as `id`, `name`, `description`, `images`, `owner`, `public`, `tracks`, `type`, and `uri`.
- This endpoint returns playlist metadata, but another endpoint is needed to fetch the actual tracks inside a playlist.
- For SoundPrint, this endpoint is useful because playlists can reveal user taste groupings through themes, moods, and categories.

### Audio Features / Audio Analysis

- Spotify's track audio features endpoint is marked as deprecated.
- This means that SoundPrint should not depend on Spotify audio features.
- Spotify also notes that Spotify content may not be used to train ML or AI models.
- The MVP should focus on available data instead of training a model on this Spotify content.

### Related Artists

- Spotify's related artists endpoint is also marked as deprecated.
- This means that SoundPrint should not depend on Spotify's related artists endpoint for recommendations.

### Artist Genres

- Spotify's artist `genres` field is marked as deprecated.
- This means that SoundPrint should not depend on Spotify's artist genres as a recommendation signal.


### Recommendation Method

- Use the user's top artists, top tracks, playlists, and recently played tracks as the main recommendation signals.
- Since Spotify audio features, related artists, and artist genres are deprecated, SoundPrint should avoid depending on those features.
- For the MVP, recommendations should be based on the Spotify data I can still access.
- One approach would be to find candidates of songs/artists that overlap with the user's top artists, top tracks, playlists, and recently played tracks.
